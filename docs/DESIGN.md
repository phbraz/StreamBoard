# StreamBoard — Design

A LAN stream deck. Any device on the local network (PC, laptop, phone) opens a
web UI served by the **target PC** and presses buttons. The target plays sounds
(into Discord/OBS via a virtual mic) and runs actions (hotkeys, mic mute, later
OBS control).

## 1. Goals and non-goals

**Goals**

- Zero install on client devices — a browser is enough.
- Each client device has its **own board** (layout + sounds) and can upload
  sound files to the server.
- Sounds play on the target with low latency, can overlap, and are routed into
  a virtual microphone so Discord/OBS/games hear them.
- Actions: send keypresses/hotkeys, mute/unmute mic. OBS later.
- Live state on every connected device (now playing, mic muted).
- Safe on a shared LAN: devices must pair; clients can only trigger actions the
  server defines.

**Non-goals (for now)**

- Access from outside the LAN.
- Windows/macOS target support (keep the door open, but Linux + PipeWire +
  Hyprland first).
- Sharing sounds between devices' boards.
- Playing sounds on the client device.

## 2. Architecture

```
 ┌───────────────┐        HTTP  (UI, pairing, uploads, board edits)
 │ Browser       │ ─────────────────────────────────────────────┐
 │ PC / laptop / │                                              ▼
 │ phone         │ ◄──── WebSocket (play, actions, ack, state) ──►┌──────────────────────────────┐
 └───────────────┘                                                │ soundboard server (Rust)     │
                                                                  │                              │
                                                                  │  web     axum: static UI,    │
                                                                  │          REST, WebSocket     │
                                                                  │  auth    pairing + tokens    │
                                                                  │  store   boards + sound files│
                                                                  │  audio   decode, mix, play   │
                                                                  │  actions keys / mic / obs    │
                                                                  └──────┬──────────────┬────────┘
                                                                         │              │
                                                              PipeWire "Soundboard"   wpctl / ydotool /
                                                              sink → virtual mic      hyprctl / (obs-ws)
```

One process on the target does everything. The React UI is built by Vite and
embedded into the server binary, so in production the browser just opens
`http://<target>:7878` (or `http://soundboard.local:7878`).

## 5. Data and configuration

Paths follow XDG:

- Config: `~/.config/soundboard/config.toml`, `~/.config/soundboard/actions.toml`
- Data: `~/.local/share/soundboard/`

```
~/.local/share/soundboard/
  devices.json                      # paired devices: id, name, token hash, created
  devices/<device-id>/
    board.json                      # this device's layout
    sounds/<sound-id>.<ext>         # uploaded originals
```

### `config.toml`

```toml
[server]
bind = "0.0.0.0:7878"
mdns = true                      # advertise soundboard.local

[audio]
output = "soundboard_sink"       # PipeWire node to play into; "default" for speakers
master_volume = 1.0
max_upload_mb = 20

[mic]
source = "@DEFAULT_AUDIO_SOURCE@"  # the REAL mic, not the virtual one
```

### `actions.toml` — server-defined actions only

Clients can only reference these by `id`. They can never send commands.

```toml
[[action]]
id = "mic-toggle"
label = "Mic"
kind = "mic"
op = "toggle"                    # toggle | mute | unmute

[[action]]
id = "discord-deafen"
label = "Deafen"
kind = "keypress"
keys = "ctrl+shift+d"
backend = "ydotool"              # ydotool | hyprctl

[[action]]
id = "obs-record"
label = "Record"
kind = "hyprctl_shortcut"
keys = "CTRL SHIFT, R"
window = "class:com.obsproject.Studio"

# later:
# [[action]]
# id = "obs-scene-game"
# kind = "obs"
# request = { type = "set_scene", scene = "Game" }
```

An optional `kind = "shell"` may be added later. It's only definable in this
file, never through the UI.

### `board.json` (per device)

```json
{
  "version": 1,
  "columns": 4,
  "buttons": [
    { "id": "b1", "kind": "sound",  "soundId": "s_8f2c", "label": "Airhorn",
      "color": "#e11d48", "volume": 0.8, "mode": "overlap" },
    { "id": "b2", "kind": "action", "actionId": "mic-toggle", "label": "Mic" },
    { "id": "b3", "kind": "empty" }
  ]
}
```

Sound `mode`: `overlap` (default), `restart` (stop own previous instance), or
`toggle` (press again to stop).

## 6. Pairing and auth

1. On startup the server prints the URL, a 6-digit **PIN**, and a **QR code**
   that encodes `http://<lan-ip>:7878/pair?pin=123456`.
2. The device opens the URL, enters a name ("Phone"), and calls
   `POST /api/pair { pin, name }`. The response is `{ deviceId, token }`.
3. The token is stored in `localStorage`. The server stores only its hash.
4. HTTP calls send `Authorization: Bearer <token>`. WebSocket connections
   authenticate with the first `hello` message, because browsers can't set
   headers on WebSocket connections.
5. The PIN rotates after each successful pairing and on every restart. Devices
   can be revoked from the server CLI (and later the UI).

## 7. HTTP API

All routes except `/api/pair`, `/api/health`, and the static UI need a bearer token.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | liveness |
| POST | `/api/pair` | `{pin, name}` → `{deviceId, token}` |
| GET | `/api/board` | this device's board |
| PUT | `/api/board` | replace board (validated) |
| GET | `/api/sounds` | list this device's sounds |
| POST | `/api/sounds` | multipart upload (`file`, optional `label`) → sound metadata |
| DELETE | `/api/sounds/:id` | delete sound (and clear buttons using it) |
| GET | `/api/actions` | server-defined actions (id, label, kind) |
| GET | `/ws` | WebSocket upgrade |

**Upload rules:** size ≤ `max_upload_mb`. Formats mp3, ogg/opus, wav and flac,
checked by actually probing the file with symphonia (not by trusting the
extension). Files are stored under a server-generated ID, never under the
client's filename.

## 8. WebSocket protocol

JSON text frames, tagged by `type`. Types are defined in `server/src/protocol.rs`
and exported to TypeScript.

### Client → server

```jsonc
{ "type": "hello", "token": "…" }                       // must be first
{ "type": "play", "requestId": "r1", "soundId": "s_8f2c" }
{ "type": "stop", "requestId": "r2", "soundId": "s_8f2c" }
{ "type": "stopAll", "requestId": "r3" }
{ "type": "runAction", "requestId": "r4", "actionId": "mic-toggle" }
{ "type": "ping" }
```

### Server → client

```jsonc
{ "type": "welcome", "deviceId": "d_1", "serverVersion": "0.1.0", "state": { … } }
{ "type": "ack", "requestId": "r1", "ok": true }
{ "type": "ack", "requestId": "r4", "ok": false, "error": "ydotoold not running" }
{ "type": "state", "state": { "micMuted": false, "playing": [ { "soundId": "s_8f2c", "deviceId": "d_1" } ] } }
{ "type": "boardUpdated" }                             // refetch via HTTP
{ "type": "error", "message": "not authenticated" }
{ "type": "pong" }
```

- `ack` answers one request. It confirms the sound actually started, or the
  action actually ran.
- `state` is broadcast to **all** connected devices whenever the playing set or
  mic state changes. The server also polls the mic state every ~2s, so
  mutes made outside the app show up too.
- If the first message isn't a valid `hello` within 5s, the server closes the
  connection. The client reconnects with backoff, and the UI shows the
  connection status.

## 9. Audio

- **Decode once:** on upload or startup, decode with symphonia, resample to
  the output rate, and keep the PCM in memory (an LRU cache with a size cap if
  libraries grow big). This makes playback instant.
- **Mixer:** one output stream into the configured PipeWire node. Each `play`
  adds a voice (sound × button volume × master volume). There's a voice limit
  (e.g. 16) and a soft clipper.
- **Routing (PipeWire):** a config dropped into
  `~/.config/pipewire/pipewire.conf.d/soundboard.conf` creates:
  - `soundboard_sink`: the server plays here.
  - `soundboard_mic`: a virtual source (`Audio/Source/Virtual`) that mixes the
    real mic with `soundboard_sink`'s monitor. You select this in Discord/OBS.
  - A loopback from `soundboard_sink` to your default output so you can hear
    sounds too, with its own volume.
  
  `scripts/setup-pipewire.sh` installs it and restarts PipeWire. The exact
  config gets verified in milestone 3.
- **Discord settings:** input device "Soundboard Mic", noise suppression set
  to None or Standard (Krisp eats sound effects), echo cancellation off.

## 10. Actions

```rust
trait Action { async fn run(&self) -> Result<()>; }
```

| kind | Implementation | Notes |
|---|---|---|
| `mic` | `wpctl set-mute <source> 1/0/toggle`, state via `wpctl get-volume` | Mutes the **real** mic; soundboard audio still reaches the virtual mic. |
| `keypress` + `ydotool` | `ydotool key …` | Kernel-level input, so every app sees it. Needs `ydotoold` running and `/dev/uinput` access. |
| `hyprctl_shortcut` | `hyprctl dispatch sendshortcut MODS, KEY, WINDOW` | No daemon; targets a specific window; Hyprland only. |
| `obs` (later) | `obws` client to obs-websocket v5 | Scenes, mute sources, record/stream toggles. |

Commands are spawned with argument arrays (never through a shell), with a
timeout. Failures come back in `ack.error`. On startup the server checks that
the tools it needs exist and logs a warning if one is missing.

## 11. UI (React + Vite + Tailwind)

- **Routes:** `/pair`, `/` (board), `/edit` (board editor + uploads), `/settings`.
- **Board:** a responsive grid with the column count from `board.json`. Buttons
  show their label and colour, a playing indicator, and toggle state (mic). A
  sticky "Stop all" button and a connection status dot.
- **Editor:** add, edit or remove buttons, upload sounds, pick an action from
  `/api/actions`, and drag to reorder.
- **Theming:** Tailwind v4 `@theme` CSS variables (`--color-board-bg`,
  `--color-button`, radius, gap) so the board can be restyled in one place.
- **State:** a small WebSocket client hook (`useSoundboard`) that handles
  reconnects, request ids, and acks, plus the latest broadcast `state`.
- **Dev:** Vite dev server on :5173 forwards `/api` and `/ws` to the server on :7878.

## 12. Security summary

- LAN only; bind address is configurable.
- Pairing PIN, then a per-device bearer token (only hashed tokens are stored).
- Clients reference sounds and actions by ID only. No client-supplied commands,
  paths, or filenames ever reach the filesystem or a process.
- Upload size limit and content probing.
- Rate limit on `/api/pair`.
- HTTPS is not used in v1 (plain HTTP on the LAN). That limits some web-app
  install features but nothing the app depends on.

## 13. Milestones

1. **Skeleton:** workspace, axum server with `/api/health` + `/ws` hello/welcome,
   embedded UI, Vite+React+Tailwind app with dev proxy, ts-rs type export.
2. **Pairing + storage:** devices, tokens, per-device boards, uploads.
3. **Audio:** decoding, mixer, playback into a PipeWire node, setup script,
   `play`/`stop`/`stopAll` with acks and `state` broadcast.
4. **Actions:** mic (with state polling), ydotool keypress, hyprctl shortcut.
5. **UI:** board, editor, uploads, theming, reconnect handling.
6. **Polish:** QR code + mDNS, systemd user service, packaging.
7. **Later:** OBS integration, shell actions, Windows/macOS targets, HTTPS
   via our Cloudflare domain (see open questions).
